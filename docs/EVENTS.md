# Contract events and how the indexer stores them

This document is the map between the events published by the [Aidline contract](https://github.com/aidline-org/aidline-contracts/blob/main/contracts/aidline/src/events.rs) and the tables the backend writes. It is meant to be read alongside [`src/stellar/events.ts`](../src/stellar/events.ts) (decoding) and [`src/indexer/store.ts`](../src/indexer/store.ts) (storage). When you add an event to the contract, update all three.

## How an event flows through the backend

1. `Indexer.syncOnce` in [`src/indexer/indexer.ts`](../src/indexer/indexer.ts) polls Soroban RPC `getEvents`, filtered to the configured contract id, and follows the cursor from `indexer_state`.
2. Each raw RPC event goes through `decodeEvent`. The first topic is the event name; `decodeEvent` switches on it and builds a typed `AidlineEvent`, or returns `null` for a name it does not recognise. Unknown events are ignored, so a newer contract never crashes an older indexer.
3. For every decoded event that carries a `campaignId`, the indexer calls `get_campaign` on the contract and upserts that campaign **from the contract state** (this is why `raised`, `released`, `milestones_released` and `status` are copied, not summed — see [ADR 0004](adr/0004-contract-totals-not-event-sums.md)). The result is written to `campaigns` by `upsertCampaign`.
4. `recordEvent` writes the event-specific history rows below. History rows use the RPC event id as their primary key with `ON CONFLICT DO NOTHING`, so replaying a page is harmless.
5. All of it — events, campaign updates and the new cursor — happens in one database transaction per page. A failed page writes nothing and is retried on the next tick.

Every history row carries these common columns from the raw event: `event_id` (RPC event id, primary key), `ledger`, `tx_hash` and `created_at` (the ledger close time). They are not repeated in the table below.

## Decoding notes

- **Topic names.** The "Contract topics" column is the symbol the contract publishes in `events.rs` (`symbol_short!` values such as `created`, `released`, `verifier`). `decodeEvent` currently switches on the longer names shown in the "Indexed as" column (`campaign_created`, `milestone_released`, `campaign_cancelled`, `verifier_updated`; `donated`, `refunded` and the contract's symbols line up). If a deployed contract emits a name the decoder does not match, that event is silently ignored. Check the event name a `getEvents` response actually carries before assuming a new event is indexed — the unit tests in [`test/events.test.ts`](../test/events.test.ts) show the topic shapes the decoder expects.
- **Topics versus data.** The decoder reads identifiers from the topic list (`campaign_id`, `donor`, `verifier`, `index`) and amounts/flags/URIs from the value map (`amount`, `index`, `proof_uri`, `active`). This is a contract convention: topics are the small indexed keys, data is the payload.
- **Amounts** are `i128` in the contract, read as `bigint` by `decodeEvent` and stored as strings in `NUMERIC(39, 0)` columns. Never pass them through `Number()` (see [ADR 0003](adr/0003-amounts-are-numeric-strings.md)).
- **Metadata and proofs** are linked by URI. `upsertCampaign` sets `campaigns.metadata_id` only if the metadata was created locally through `POST /metadata`; `recordEvent` sets `milestone_releases.proof_id` only if the proof was uploaded locally through `POST /proofs`. A foreign URI is stored as-is without a foreign key link.
- **History is not totals.** `donations`, `refunds` and `milestone_releases` power timelines and CSV export. The numbers in `campaigns.raised`, `campaigns.released` and `campaigns.status` always come from the contract. See [ADR 0004](adr/0004-contract-totals-not-event-sums.md).

## Adding a new event

The pledge, verifier-bond and emergency-advance events are stored in `pledge_events`, `verifier_bond_events` and `emergency_advances`; their current projections are exposed through the campaign, donor and verifier endpoints.

1. **Contract first.** Add the struct and its `publish` implementation in `events.rs` and decide which fields are topics (identifiers) and which are data (payload).
2. **Decode it.** Add a case to `decodeEvent` in `src/stellar/events.ts` and a variant to the `AidlineEvent` union. Keep the `eventId`, `ledger`, `txHash`, `closedAt` base fields. Return `null` for anything you do not handle.
3. **Store it.** Add a `case` to `recordEvent` in `src/indexer/store.ts`. For a new table, add a numbered migration in `src/db/migrations/` (never edit an existing migration). Use the RPC event id as the primary key and `ON CONFLICT DO NOTHING`. If the event carries a `campaignId`, `upsertCampaign` will already refresh that campaign from the contract — you do not need to update totals yourself.
4. **Test it.** Add a raw-event builder in `test/helpers.ts` and decoding/storage tests in `test/`.
5. **Document it.** Add a row to the table above, including events you deliberately do not index, so the next contributor can see the gap. Update this file whenever `events.rs` changes.
